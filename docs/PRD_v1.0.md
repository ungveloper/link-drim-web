# 링크드림 (LinkDrim) — 제품 요구사항 명세서 (PRD)

- 문서 상태: 8차 인터뷰(Q1~Q110) 완료 기반, **서비스 네이밍 확정·저장소 확인 전 설계 초안 v1.0**
- 정리 기준일: 2026-10-29
- 제품명: **링크드림 (LinkDrim)** / 메인 도메인: **linkdrim.com** (사용자 선택 완료, 실제 구매·소유 여부 미확인)
- 상위 브랜드: **홀로기업** / 슬로건 초안: **당신을 소개하는 링크를 드림.** (문구는 미확정)
- 프로젝트 단계: 요구사항 인터뷰 완료 → 서비스 이름·도메인 선택 완료 → 기존 GitHub 저장소 분석 → DB/화면/API 상세설계 보정 → 구현·테스트
- 핵심 목표: 컴퓨터에 익숙하지 않은 1인 기업 대표·전문직 개인이 하나의 관리 화면에서 공통 데이터를 입력해 여러 종류의 브랜딩 페이지를 쉽게 운영하고, 유입·클릭·행동을 이해하도록 하는 서비스
- 초기 고객 규모: 약 5~10개 사이트, 초대 기반 비공개 온보딩. 초기 개발·개인 검증은 비용 최소화, 고객 납품용 상업 배포에는 상업용 호스팅 정책 준수.

> 이 문서는 인터뷰 답변의 집계이며 구현 완료나 법률 적합성·도메인 가용성·비용을 보장하지 않는다. 신규 확인이 필요한 항목은 `검증 필요`로 표시한다.

## 1. 제품 원칙

1. 고객의 관리자 UI는 **성과 분석**과 **페이지 관리**의 2개 메뉴만 제공한다. PC 좌측 사이드바, 모바일 햄버거 메뉴. 다수 사이트 권한자는 상단 사이트 선택기로 전환한다.
2. 사용자는 디자인을 자유 제작하는 빌더 대신 제작 완료된 템플릿의 더미 미리보기를 보고 활성화한다. 활성 템플릿별 필수 필드를 수집하되 **공통 필드는 입력 폼에 1회만 표시**한다.
3. 한 사이트가 공유하는 프로필 데이터는 선택한 모든 페이지에 재사용한다. 템플릿에서는 필요 필드와 레이아웃을 선택하고, 초기에는 항목 순서(특히 링크)와 테마 색상/배경 등 제한된 커스터마이징만 허용한다.
4. 고객은 자신이 관리 가능한 사이트의 콘텐츠·통계를 변경/조회하지만, 이력 조회·롤백·초기화·멤버 초대/회수는 하지 못한다.
5. 운영자는 강력한 고객·계정·템플릿·오류·이력·복구 기능을 `/admin`에서 사용한다. 고객은 `/dashboard`를 사용한다.
6. 저장이 성공하면 실시간으로 공개 페이지에 반영한다. 유효하지 않은 저장은 거부하고 이전 정상 공개 상태를 보호한다.
7. 초기에는 불특정 다수 가입, 결제/상품판매, 자동 DM, 알림톡, AI 생성, GA4 픽셀 연동을 구현하지 않는다. 장래 확장 가능성은 고려한다.

## 2. 사용자, 역할, 사이트 연결

- `super_admin`: 초기에 1명. 모든 고객/페이지/오류/권한/스냅샷/템플릿과 전체 내보내기 관리. 추가 super_admin을 미래에 안전하게 임명할 수 있도록 역할 분리.
- `platform_admin`: 최고 관리자가 임명할 추후 운영자. 최고 관리자와 다른 역할로 선언하며 권한은 최소 부여, 범위는 실제 운영 필요에 따라 지정. 초기에는 최고 관리자 1명만 필수.
- `site_member`: Google/Naver/Kakao 로그인 후 초대 수락한 고객 사이트 관리자. 같은 사용자가 여러 사이트 관리 가능하며 같은 사이트에 여러 site_member가 있을 수 있음. 다른 멤버 초대/회수 권한 없음.
- 플랫폼 사용자와 고객 사이트는 다대다 관계이며, 사용자 계정과 고객 사이트의 고유 ID는 분리한다. 사이트별 권한 회수는 해당 사이트에만 적용한다.
- 최고 관리자가 사이트 생성 → 템플릿/초기 데이터 구성 → 초대 링크 제공 → 소셜 로그인 후 연결 → 고객 편집 개시. 초대 링크: 7일 유효, 1회용, 재발급 가능, 원문 토큰 저장 금지, 수락 검증/사용 처리 원자적으로 수행. 계정 오연결 시 특정 멤버만 회수하거나 사이트 전체 접근을 초기화하고 건별 초대를 재발급 가능.
- 초대 링크의 전달/탈취 위험은 별도 검증(추가 확인 코드 또는 채널 검증)과 속도 제한을 구현 전 보안 검토. 동일 이메일이라는 이유만으로 관리자 권한 부여 금지.
- 일반 로그인 후 기본 진입 화면은 성과 분석, 신규 초대/초기 정보 부족 시 페이지 관리로 안내. 고객이 기본 진입 화면을 두 메뉴 중 변경할 수 있도록 한다.

## 3. URL·도메인·공개 정책

- 플랫폼 경로: `https://linkdrim.com/{site_slug}/profile`, `/{site_slug}/business-card`, `/{site_slug}/link`.
- 공통 템플릿의 `/profile`, `/business-card`, `/link` 경로 문자열은 고정. 맞춤 템플릿 경로는 최고 관리자가 코드 배포 시 정의하며 고객이 변경하지 않는다.
- 고객이 수정할 수 있는 것은 `{site_slug}`뿐이며, `site.id`는 불변 UUID. `site_slug`는 플랫폼 전체 UNIQUE 및 시스템 예약어 제한(`api`, `admin`, `dashboard`, `login` 등), URL 구문 검증. 입력 중 사용 가능 여부를 미리 확인하되 최종 DB UNIQUE 제약과 단일 트랜잭션에서 재검증. 이전 slug는 예약·유지·리디렉션하지 않는다. 변경 시 공유 URL 단절 경고 필수.
- 고객별 구매 도메인 연결: DNS 안내, 복사, 상태(설정 필요/확인 중/완료/오류), 연결 검증/주기적 소유권 확인, SSL, `www` 변형 처리 검토. 고객 도메인 루트(`/`)에는 선택한 대표 활성 템플릿을 보이며 `/profile`, `/link` 등 동일한 고정 경로 사용. 일반 플랫폼 기본 경로에서는 사이트 slug 필요.
- 고객은 대표 템플릿 1개 설정. 대표 템플릿을 해제할 때 다른 활성 템플릿을 고르도록 안내. 모두 비활성화되면 사이트 준비 중 상태.
- 비활성 템플릿 경로는 HTTP 404와 안내 문구. 처음 정상 공개되지 않은 페이지는 준비 중 안내. 일시 중지/삭제 대기 상태는 별도 정책 적용.
- SEO: 사이트 공통 설정 한 묶음(검색 허용 여부, 제목/설명 선택적 재정의, OG 이미지 및 자동 생성 메타데이터, canonical 대표 도메인). 상세 편집 UI는 접기 형식. 비공개/비활성 콘텐츠의 색인은 금지하고 검색 비노출은 접근 통제와 구분해 설명.

## 4. 템플릿·공통 입력

- 초기 공용 템플릿 3개: `profile`, `business-card`, `link`. 필요 시 업종별 공용 템플릿 추가. 새 공용 템플릿은 기존 고객 UI에 `NEW`로 표시되고 기본 선택은 OFF.
- 최고 관리자가 Next.js 컴포넌트 + 버전별 필드 정의로 템플릿 개발·등록·테스트·공개/중지. 고객이 코딩 없이 임의의 새 레이아웃을 만드는 기능은 없음.
- 공개 템플릿(`public`)은 모든 고객에 노출. 전용 템플릿(`private`)은 지정 사이트만 접근·사용 가능하며 코드/DB/API 권한 모두 격리.
- 각 사이트/템플릿 종류 당 활성 디자인 버전 하나. 기존 사용 버전은 자동 변경하지 않으며 새 버전 출시 시 Sonner 알림 + 더미/실데이터 미리보기 + 명시적 업그레이드 버튼 제공. 고객은 **상위 버전으로만 이동**할 수 있고 직접 다운그레이드할 수 없다는 안내를 업그레이드 전에 제공. 최고 관리자의 사고 복구용 스냅샷·이전 코드 보존은 별도 운영 기능.
- 템플릿 버전은 코드 및 필드 스키마가 함께 보존되어야 함. 과거 버전 참조 데이터도 삭제하지 않는다. 신규 필드 기본 선택 입력, 버전 업그레이드 시 필수값 충족 검증 후 전환.
- 공통 프로필 후보: 이름, 사진, 한 줄 소개, 상세 소개, 직함/업체명(선택), 전화, 이메일, SNS 주소, 대표 링크, 이미지·소개 콘텐츠 등. 필요 필수 여부는 템플릿 필드 스키마로 결정. 맞춤 템플릿 확장은 JSONB 보조 데이터 사용.
- 기본 테마: Primary/Secondary/Background 3개 색상, 기본 블랙/화이트 및 중립 보조색. 고객은 허용된 배경 이미지·대표 이미지·색상 변경 가능. 대비 자동 보정 및 접근성 유지.
- 선택 템플릿들에 필요한 필드를 집합(유니온)으로 계산해 하나의 입력 폼을 동적 생성. 템플릿을 해제해도 해당 데이터는 삭제하지 않음. 기능은 PC/모바일 동일.
- 미리보기: 더미 디자인 미리보기는 언제든지 가능, 실제 고객 데이터 미리보기는 해당 템플릿 필수값 검증 통과 시 제공.

## 5. 링크·명함 특성

- 링크 개수는 제품 정책상 무제한(물리적 저장소·요금제 사용량 제한은 존재함). 제목/URL/이미지/아이콘/표시 여부/정렬, 상단 고정, 드래그 정렬과 위·아래 버튼 모두 제공. 초기에는 공개/비공개만 제공하고 예약 게시/종료는 후속 버전.
- 링크 레이아웃: 전체 목록 단위로 리스트형 또는 카드형 선택. 개별 링크마다 임의의 레이아웃 지정하는 복잡한 빌더는 제외.
- 디지털 명함: 이름/전화/이메일 등의 vCard 다운로드, QR코드 공유.
- 외부 링크 외 `tel:`, `mailto:`, 카카오톡 링크를 허용하고 클릭 유형별 이벤트를 기록. 클릭/이동은 실제 통화·문의·예약 완료와 다름을 명시.
- 인스타그램·Threads·네이버 블로그·카카오톡·유튜브 등 공유 채널별 UTM 추적 URL을 손쉽게 복사하는 기능.

## 6. 편집·저장·동시 수정

- 관리 UI는 동일 URL 안의 접이식 섹션 중심, 메뉴는 2개만. 일반 사용자 기준으로 문구·버튼·오류 메시지를 간결하고 직관적으로 작성. 이미지 선택/자르기/위치·확대 축소/압축 최적화, 파일 타입·크기 검증 및 서버 재검증.
- 고객이 명시적으로 `저장`을 눌러 공개 반영. 필수값 누락 시 저장 차단, 첫 오류 필드에 포커스·스크롤, 필드별 도움말 표시, 운영 오류 테이블에 중복 집계 가능한 사건 기록. 저장 버튼 중복 클릭 방지 및 서버 중복 요청 방지.
- 마지막 정상 공개 콘텐츠/템플릿 버전 보유. 편집 실패는 기존 공개 데이터를 보호. 첫 정상 공개 전에는 준비 중 화면.
- 이탈 시 미저장 변경 경고. 모바일 종료·재방문 대비 임시 편집 정보 보존(기본적으로 클라이언트 초안; 기기/버전 충돌 예방), 임시 내용은 공개 DB에 자동 덮어쓰지 않음.
- 변경 전 서버의 최신 revision을 검증하고 동일 revision일 때만 저장하는 낙관적 잠금(트랜잭션·조건부 갱신). 누군가 변경했으면 저장 차단 및 충돌 안내, 무음 덮어쓰기 금지. 새 revision 생성과 변경 이력 저장은 원자적 처리.
- 최고 관리자만 버전 목록과 필드별 diff(GitHub식 추가·삭제 비교), 전체 복구/초기화 가능. 복구/초기화도 새 이력으로 남긴다. 초기화 전에 고객 사이트명 재입력 등 강한 확인. 복구/초기화 범위는 콘텐츠, 링크, 템플릿, 대표 페이지, 테마이고 통계·소셜 권한·도메인 소유권 기록은 롤백하지 않음.
- 과거 이미지 복구를 위해 이전 버전이 참조하는 최적화 이미지 자산을 유지하고, 필요하면 아카이브. 일반 고객에게 히스토리 메뉴를 노출하지 않음.

## 7. 분석·성과 화면

- 첫 화면은 30/90일/1년 선택. 핵심 지표는 페이지 조회수, 세션, 추정 고유 방문자, 클릭 및 클릭률, 평균 활성 체류 시간(추정). 방문 추이, SNS·UTM 유입 채널, TOP 5 링크, 시간대, 페이지 간 이동/클릭 순서(익명), 간결한 자동 성과 설명. 세부 흐름은 접어서 제공.
- 공개 페이지 이벤트: `page_view`, `page_navigation`, `link_click`, `phone_click`, `email_click`, `booking_link_click`, `active_duration` 등. 이벤트명·버전·속성/타임존 정의는 구현 시 최종 확정.
- 인스타그램/Threads 등의 referrer가 누락될 수 있으므로 직접/알 수 없음 범주를 유지하고 UTM의 출처를 더 높은 우선순위로 해석. 표준 UTM 파라미터를 활용하며 URL 악용·중복 이벤트·봇 트래픽을 통제.
- 미리보기와 운영자가 명시적으로 검증용으로 연 페이지는 분석 제외. 공개 URL의 관리자 접속은 구분 가능한 방식 검토. IP 하나로 운영자 제외하지 않음.
- 통계 수집 실패가 방문·외부 이동을 방해하지 않도록 비차단 처리. 오류 수집 및 통계 신뢰도/누락 기간 표시.
- 원시 이벤트는 운영 DB에 최근 90일 기준 유지, 이전 데이터는 장기 저장소로 아카이브, 일·월 집계는 장기 보존. 보존 비용과 개인정보 정책을 지키면서 실제 이용량에 따라 조정.
- 사람을 직접 식별하는 IP, 토큰, 연락처 등을 통계 이벤트에 장기간 무차별 저장하지 않음. 익명·가명 이벤트·추정치, 보관/삭제/고지 정책을 제품화.
- 초기에는 자체 수집, GA4/메타픽셀 등 외부 추적 도구는 후속 확장.

## 8. 오류 기록 및 Notion 동기화

- 별도 Supabase 오류 원장(사건 ID, 사이트 ID, 종류/심각도/발생·최근 시각, 건수, 상태, 해결자, 재현 맥락, 동기화 상태) + 이 서비스 전용 Notion 데이터베이스.
- 클라이언트 검증 누락, 이미지 업로드, 로그인, 도메인, 템플릿 렌더링, 통계 수집, API/DB/Notion 연동 장애 포함. 사용자에게 발생하는 정상적인 입력 오류와 실제 서비스 장애는 심각도를 구분.
- 동일 사이트+필드+오류 지문 등으로 반복 이벤트를 단일 사건으로 묶고 횟수 갱신. 같은 버튼을 여러 번 눌러 Notion 페이지가 무한 생성되지 않도록 Idempotency 적용.
- Supabase를 원장으로 하고 Notion과 양방향 상태 동기화. Notion 변경 이벤트 서명 검증, 후속 최신 상태 조회, 버전/수정 시각 충돌 감지, 루프/중복 방지 및 재시도·데드레터 보존. 해결 완료를 어느 쪽에서 처리해도 반영되도록 함.
- 별도 SMS/메일/Slack 알림을 앱에서 만들지 않음. 사용자가 Notion의 자동화를 직접 구성함. Notion DB ID·속성·Integration 비밀키는 구현 시 안전하게 제공받아 서버 환경 변수로 관리.
- 오류 로그/Notion 기록에는 인증 토큰, 초대 토큰, 민감정보, 과도한 개인 데이터 포함 금지.

## 9. 사이트 상태·SEO·운영

- 사이트 상태: `active`, `suspended`, `pending_deletion`; 사용자가 직접 삭제 불가, 최고 관리자만 변경/복원/최종 삭제. 법적 삭제 요청과 보존 의무는 정책으로 정함.
- 신규 템플릿은 관리자 검증 환경에서 시험 후 공개, 문제 발생 시 배포 중단. 고객이 버전을 고정 중이라도 긴급한 보안·장애 조치에 필요한 롤아웃/차단 정책은 별도 보유.
- 새 주소 및 고객 도메인을 내보낼 때 canonical·OG·robots·사이트맵 처리. 사용자 slug 변경 전 경고. 구 경로 자동 이동은 없음.
- 고객 데이터 내보내기: 고객은 자신이 관리하는 사이트의 프로필/링크 JSON·CSV, 최고 관리자는 고객별 콘텐츠/설정/이력/집계 통계 내보내기. 인증 정보, 초대 토큰, 타 고객 데이터 제외.
- 사이트 초기 생성: 사이트 이름, slug, 최초 템플릿, 공개 상태. 고객 정보와 운영 메모는 최소한으로 시작.

## 10. 권장 논리 데이터 모델 (정식 SQL은 저장소 조사 후)

| 논리 엔터티 | 역할과 핵심 관계 |
|---|---|
| `users` / `user_identities` | 로그인 주체, 공급자+고유 subject, 사용자 기본 진입 화면 |
| `sites` | 불변 UUID, UNIQUE slug, 상태, 대표 템플릿, SEO 공통 설정 |
| `site_members` | 사이트↔사용자 다대다, 권한·연결 상태 |
| `platform_roles` | super_admin/platform_admin 할당, 독립 인증 보강 |
| `invitations` | 사이트, 토큰 해시, 만료, 사용 시간, 회수 상태 |
| `site_profiles` | 기본 공유 프로필 필드, 확장 JSONB |
| `site_links` | 링크 종류·정렬·고정·노출·표시 메타데이터 |
| `site_appearance` | 공통 3색 테마·이미지 등 |
| `template_catalog` | 템플릿 종류, 공개/전용, 지정 사이트, 고정 path |
| `template_versions` | 불변 버전, 필드 스키마, 컴포넌트 키/배포 상태 |
| `site_template_selections` | 사이트별 활성화, 선택 버전, 버전 알림 상태 |

| `domains` | host→사이트 매핑, DNS 검증 및 canonical |

- 모든 테넌트 테이블은 `site_id`를 기준으로 경계를 만들고 사용자·서비스 권한을 DB RLS 및 서버 측 접근 검증으로 강제.
- 공개 콘텐츠 조회는 공개 가능한 필드만 노출하는 서버 쿼리/뷰를 사용. 초대·권한·원시 내부 오류는 공개 질의에서 배제.
- URL slug와 각종 템플릿 경로, 도메인 식별은 UNIQUE 및 예약어 정책과 함께 검증.

## 11. 기술 스택 및 배포

- Next.js App Router + TypeScript, Tailwind CSS + shadcn/ui, Zod, Supabase PostgreSQL/Auth/Storage, Vercel, Vitest + Playwright.
- 인증: Google, Kakao는 Supabase 지원 경로를 활용. Naver는 실제 공급자 인증·callback·연결 테스트를 거쳐 확정할 통합 경로 필요. 무료·유료 요금제 기능 제한을 구현 전에 재검증.
- 초기 규모 약 5~10개 사이트, Vercel Hobby는 **비상업적 개발·개인 검증만**. 실제 상업적 고객 납품 단계에서 Vercel Pro 등 해당 정책에 맞는 계획 사용.
- 로컬 개발/테스트·미리보기/운영 환경 분리. 테스트 DB는 실제 고객 데이터와 분리, 마이그레이션과 RLS 검사 자동화. 실제 운영 배포 전에 테스트 통과·검토 게이트.
- 성능: 모바일 우선, 320px에서도 레이아웃 정상, 큰 글자·터치 타깃, 이미지 최적화, 접근성/메타데이터 점검. 분석 오류가 페이지 경험에 영향을 미치지 않게 함.
- 백업: DB 덤프와 Supabase Storage 이미지 별도. 주기적 복원 실험 필요. 애플리케이션 장애 전반에 대해 캐시가 마지막 공개 버전을 항상 제공한다고 가정하지 말 것.
